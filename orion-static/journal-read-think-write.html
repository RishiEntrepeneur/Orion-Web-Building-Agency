Read, think, write

Why your scroll animation stutters, and why it is almost never the easing curve.

14 August 2026 6 min read Build note

A scroll-linked animation that judders is usually blamed on the wrong thing. People reach for a different easing curve, then a shorter duration, then a smooth-scroll library. The curve is rarely the problem. The problem is that the browser is being asked to lay the page out twenty times in a single frame.

What forces a layout

The browser batches style changes. Write to style.transform and nothing happens immediately — the change is queued. But ask a question whose answer depends on layout, and the browser must stop and compute everything queued so far before it can answer.

  • getBoundingClientRect()
  • offsetTop, offsetWidth, clientHeight
  • getComputedStyle() for a computed length
  • scrollWidth, scrollHeight

One read after one write is cheap. The trouble is the shape almost everyone writes without thinking: a loop over animated elements, measuring each one and then styling it.

for (const el of items) {
  const r = el.getBoundingClientRect();   // read
  el.style.transform = compute(r);        // write
}                                          // ...and round again

Every iteration after the first forces a synchronous layout, because the previous iteration's write invalidated what the next read needs. Ten elements is ten full layout passes. Put four such loops in one frame and the frame budget is gone before anything is painted.

The easing curve describes the motion you asked for. Layout thrashing decides whether you get it.

The fix is ordering, not cleverness

Split the frame into phases and never interleave them. Read everything, then compute everything, then write everything:

function frame(t) {
  runPhase(readers, dt, t);   // every measurement in the app
  runPhase(tickers, dt, t);   // maths only, no DOM
  runPhase(writers, dt, t);   // every style and attribute
  requestAnimationFrame(frame);
}

Callbacks register into the phase they belong in rather than being written as one function. It reads slightly worse and runs enormously better: one layout pass per frame regardless of how many elements are animating.

Two things that catch people out

First, event handlers count. A pointermove handler that measures an element runs between frames, and lands after that frame's writes — which is exactly the forced layout you just eliminated. Move the measurement into the read phase and use the pointer position you already track.

Second, if the element sits inside a 3D-transformed subtree, getBoundingClientRect() returns its transformed size. A parent with translateZ(28px) under a 1500px perspective scales its children by about 2%. Measure with getComputedStyle() when you want layout dimensions, or the error will accumulate every time you use the result as a step.

How to know it worked

Do not guess. Patch getBoundingClientRect and the style setters to log an R or a W tagged with the current frame, scroll the page, and count how many frames contain a read immediately after a write. The number you want is zero.
